# v10.2.27 mechanical-kernel resolution

Production simulations request a mechanical configuration and crack-growth
coverage. They do not require a preserved `FAMILY_JSON`, snapshot archive, or
load-invariance archive.

## Default single-front workflow

For a missing or insufficient kernel, the resolver automatically:

1. fingerprints the requested orientation, specimen/BC profile, mesh, process-zone
   length and bins, interaction length, elasticity policy, crack increment, and
   topology mode;
2. generates an extension-state table through the required path coverage;
3. runs an internal deterministic, unshielded mechanics-only geometry driver;
4. serializes new fixed-crack FEM states from the live solver;
5. recalculates load invariance for every state;
6. derives normalization from the newly captured engine configuration;
7. builds and validates the signed active-kernel family;
8. caches it under `runs/v10_2_27_kernel_cache/<configuration-fingerprint>/`.

The mechanics-only geometry driver is generated by the code and is not one of the
scientific material parameterizations. For a single nonbranching front, material
kinetics determine only when the prescribed extension is reached; the frozen FEM
operator is recalculated at the requested geometry.

Changing theta, mesh, process-zone geometry, interaction length, elasticity, or
other mechanical coordinates creates a new fingerprint and triggers a new
calculation. Increasing target extension beyond cached coverage extends/rebuilds
the same configuration cache. Shorter campaigns may reuse a longer validated
cache.

## Optional caches

A family or portable mechanics archive may be supplied explicitly as an
acceleration only. It must carry the exact mechanical-configuration fingerprint
and pass field-level checks. Legacy archives without that provenance, including
the old 100 µm/40-bin theta=30 capture, are rejected.

## Current limitations

The built-in automatic provider is for one unbranched front. Branching requires a
registered `topology_cached` or `direct_fem` provider because branch interactions
cannot be represented by an extension-only atlas. A changed initial crack/specimen
geometry likewise requires a provider that maps that geometry into the low-level
mesh; it is never approximated by the default configuration.
